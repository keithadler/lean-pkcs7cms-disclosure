================ 1. Report to OpenSSL (openssl-security@openssl.org) ================
To: openssl-security@openssl.org
Subject: CMS_verify does not check the content-type attribute against eContentType

Hello,

CMS_verify() (and `openssl cms -verify`) accepts a SignedData message whose encapContentInfo.eContentType
differs from the value of its signed content-type attribute. Because eContentType is not covered by the
signature, anyone can change the content type of a validly signed message without the signing key, and it
still verifies.

RFC 5652 requires the check: "The content-type attribute value MUST match the SignedData encapContentInfo
eContentType value" (section 11.1), and the attribute must be present whenever signed attributes are
(section 5.3). The attribute is what authenticates eContentType.

In OpenSSL, crypto/cms/cms_sd.c sets the attribute from eContentType when signing
(cms_set_si_contentType_attr), and crypto/cms/cms_att.c checks on verification that it occurs once with one
value (CMS_ATTR_F_ONLY_ONE | CMS_ATTR_F_ONE_ATTR_VALUE | CMS_ATTR_F_REQUIRED_COND), but nothing compares its
value with eContentType. CMS_SignerInfo_verify_content() compares only the message digest.

Reproduction (attached relabel-repro.sh; needs only the openssl command line and python3):

    $ OPENSSL=openssl sh relabel-repro.sh
    original:
    CMS Verification successful
    relabeled (eContentType 1.2.840.113549.1.7.5, content-type attribute still id-data):
    CMS Verification successful

The script signs a message with `openssl cms -sign`, then changes one byte of eContentType (id-data to
1.2.840.113549.1.7.5). The signed attributes, including content-type = id-data, are untouched.

Versions: OpenSSL 3.6.4 (25 Aug 2026); the code is the same on master at 1e369089f4 (2026-09-27).

Impact: an application that verifies with CMS_verify() and then acts on CMS_get0_eContentType() can be
made to treat content signed as one type as another. How much that matters depends on the application
(for example RFC 3161 timestamp tokens, RPKI signed objects, S/MIME, EST and CMP all dispatch on the content
type); we have not found a specific exploitable application. The flaw needs no key material. We would rate
it low, but leave the rating to you.

Suggested fix: when signed attributes are present, compare the content-type attribute's value with
eContentType (OBJ_cmp) during verification and fail on a mismatch, as GnuTLS does in verify_hash_attr().

Found by differential testing of seven CMS verifiers against a formal specification of RFC 5652 written in
Lean (https://github.com/keithadler/lean-pkcs7cms). That repository does not mention this issue; we will
wait for your go-ahead before publishing it. LibreSSL shows the same behavior and is being told separately.

Keith Adler

================ 3. Report to Microsoft MSRC (.NET SignedCms) ================
Submit at https://msrc.microsoft.com/report/vulnerability/new (per dotnet/runtime SECURITY.md).
Attach the dotnet-repro folder (Program.cs, repro.csproj, signed.der, relabeled.der).

Product: .NET, System.Security.Cryptography.Pkcs (SignedCms)

Title: SignedCms.CheckSignature does not check the content-type attribute against eContentType

Description:

SignedCms.CheckSignature(verifySignatureOnly: true) accepts a SignedData message whose
encapContentInfo.eContentType differs from the value of its signed content-type attribute. Because
eContentType is not covered by the signature, anyone can change the content type of a validly signed
message without the signing key, and CheckSignature still succeeds while SignedCms.ContentInfo.ContentType
reports the new type.

RFC 5652 section 11.1: "The content-type attribute value MUST match the SignedData encapContentInfo
eContentType value." The attribute is what authenticates eContentType.

Steps to reproduce:

1. signed.der is an ordinary message signed with `openssl cms -sign -binary -md sha256 -nodetach`
   (content-type attribute and eContentType both id-data, 1.2.840.113549.1.7.1).
2. relabeled.der is the same file with one byte of eContentType changed, to 1.2.840.113549.1.7.5. The signed
   attributes are untouched.
3. `dotnet run -- signed.der relabeled.der` prints:

       signed.der: eContentType 1.2.840.113549.1.7.1, signature valid
       relabeled.der: eContentType 1.2.840.113549.1.7.5, signature valid

Tested with System.Security.Cryptography.Pkcs 10.0.12 on .NET 10, and 11.0.0-rc.1.26425.128 on .NET 11 RC 1,
on macOS.

Impact: an application that verifies with SignedCms and then acts on ContentInfo.ContentType can be made to
treat content signed as one type as another, with no key material. How much that matters depends on the
application; we have not found a specific exploitable one and would rate it low.

In the same testing SignedCms also accepted, among others: signed attributes with no content-type attribute
or with two of them (RFC 5652 sections 5.3 and 11.1), a countersignature among the signed attributes (section
11.4), an RSA signature one byte shorter than the modulus (RFC 8017 section 8.2.2; the same signature then has
two encodings), and a trailing byte after the message. Those need the signer's key or are malleability rather
than forgery.

Suggested fix: when signed attributes are present, require exactly one content-type attribute and compare its
value with ContentInfo.ContentType in CheckSignature.

Found by differential testing of seven CMS verifiers against a formal specification of RFC 5652 written in
Lean (https://github.com/keithadler/lean-pkcs7cms). That repository does not mention this issue; we will wait
before publishing it. OpenSSL and LibreSSL show the same behavior and are being told separately.

================ relabel-repro.sh ================
#!/bin/sh
# Changes the content type of a signed CMS message without the signing key; CMS verification still succeeds.
#   OPENSSL=/path/to/openssl sh relabel-repro.sh
set -e
OPENSSL=${OPENSSL:-openssl}
d=$(mktemp -d)
cd "$d"
"$OPENSSL" req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem -days 1 -subj "/CN=signer" 2>/dev/null
printf 'hello\n' > msg.txt
"$OPENSSL" cms -sign -binary -md sha256 -nodetach -outform DER -in msg.txt -signer cert.pem -inkey key.pem -out signed.der
echo "original:"
"$OPENSSL" cms -verify -noverify -binary -inform DER -in signed.der -out /dev/null
# encapContentInfo.eContentType is not covered by the signature; only the signed content-type attribute
# binds it (RFC 5652 11.1). Change it from id-data (1.2.840.113549.1.7.1) to 1.2.840.113549.1.7.5.
python3 - <<'PY'
b = bytearray(open("signed.der", "rb").read())
oid = bytes.fromhex("06092a864886f70d010701")
i = b.find(oid)        # the first id-data is eContentType; the one in the signed attributes comes later
b[i + len(oid) - 1] = 0x05
open("relabeled.der", "wb").write(b)
PY
echo "relabeled (eContentType 1.2.840.113549.1.7.5, content-type attribute still id-data):"
"$OPENSSL" cms -verify -noverify -binary -inform DER -in relabeled.der -out /dev/null
echo "files in $d"

================ dotnet-repro/Program.cs ================
// SignedCms accepts a message whose eContentType was changed after signing.
//   dotnet run -- signed.der relabeled.der
using System.Security.Cryptography.Pkcs;

foreach (var path in args)
{
    var cms = new SignedCms();
    cms.Decode(File.ReadAllBytes(path));
    string verdict;
    try { cms.CheckSignature(verifySignatureOnly: true); verdict = "signature valid"; }
    catch (Exception e) { verdict = "refused: " + e.Message; }
    Console.WriteLine($"{path}: eContentType {cms.ContentInfo.ContentType.Value}, {verdict}");
}

================ 4. GnuTLS (public GitLab issue, needs the signer's key) ================
GnuTLS 3.8.13 certtool --p7-verify accepts SignedData whose signed attributes hold two message-digest
attributes, if either matches: lib/x509/pkcs7.c verify_hash_attr() sets msg_digest_ok for any match and
ignores mismatches. One detached signature then verifies for two different documents.
